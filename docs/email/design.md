# メールの送信

<!-- markdownlint-disable MD013 -->

API からメールを送れるようにする（issue #32）。ウェブ（movie-log）の #37（メールのダブルオプトイン）と #38（パスワードを忘れた場合）の前提になる。

## 決まったこと

- メールはすべて API から送る。ウェブのお問い合わせも API に移す。
- 送信には Resend を使う。
- 送信先と本文は API が DB の情報から決める。フロントから送信先を受け取るメール送信用の API は作らない。
- お問い合わせと登録の API は、IP ごとの回数制限で守る。API では Turnstile を検証しない。問題が起きたら追加する。
- メールアドレスの確認が済むまで、ログインできないようにする。

## 設計

- リクエストは各機能のドメイン（user、contact）で受け取る。
- `domain/mail` には送信のインターフェースだけを置き、各 usecase から呼ぶ。S3 を扱う `media.Service` と同じ形にする。
- メールは API がリクエストを処理する中でそのまま送る。送信待ちのテーブルは作らない。送信に失敗したときは、確認メールは再送 API で、お問い合わせはユーザーの再送信で対処する。
- 利用者に送るメール（1〜4）は、日本語と英語に分ける。言語はウェブが表示している言語をリクエストで受け取る。`users` に言語の列は足さない。管理者に送るメール（5、6）は日本語にする。
- メールアドレスを変えたときは、新しいアドレスに届いた確認メールのリンクが押された時点で切り替える。それまでは古いアドレスのままにする。
- メールのリンクの有効期限は、パスワード再設定が1時間、アドレスの確認が24時間。確認メールの再送は60秒に1回まで。
- 登録画面で登録ボタンを押した後のメッセージは、登録済みのアドレスでも新しいアドレスでも「確認メールを送りました」にする。他人が登録の有無を調べられないようにするため。
- 登録済みのアドレスで登録されたときは、新しいユーザーを作らず、そのアドレスに「すでに登録されている」ことを知らせるメール（7）を送る。トークンは入れない。
- 「登録済みのアドレス」は、確認が済んだアドレスだけを指す。確認が済んでいないアドレスで登録されたときは、新しい登録として扱う。前の未確認のアカウントを今回の名前とパスワードで置き換え、確認メール（1）を送る。他人が先にそのアドレスで登録していても、持ち主が登録し直せば持ち主のパスワードになる。
- 登録済みのアドレスのときも、パスワードのハッシュを作ってから捨てる。処理の量を揃え、応答の時間の差から登録の有無がわからないようにするため。
- `users` に、メールアドレスの確認が済んだかどうかを表す列を足す。
- 確認されないアカウントは、登録から7日で削除する。
- 列を足す時点でいる既存のユーザーは、全員を確認済みにする。既存のユーザーは開発者本人だけのため。

## 基盤

### domain（`internal/domain/mail`）

```go
type Message struct {
    From     Address
    To       Address
    ReplyTo  ReplyTo  // お問い合わせのときだけ使う。空なら付けない
    Subject  Subject
    HTMLBody HTMLBody
    TextBody TextBody
}

type Service interface {
    Send(ctx context.Context, m Message) error
}
```

- 値ごとに型を作り、`NewXxx` で検証する。`Message` は `NewMessage` で作る。
- from は `Message` に持たせ、メールを組み立てる側が選ぶ。後で noreply などの from が増えても、`Service` は変わらない。
- `user.Email` の検証は `mail.NewAddress` を使う。ユーザーのアドレスは必ずメールの宛先として通るようにするため。

### infrastructure（`internal/infrastructure/mail`）

- Resend の公式の Go の SDK（`github.com/resend/resend-go/v4`）を使う。S3 と同じく、公式の SDK があるものは SDK を使う。
- エラーは `send mail: %w` で包むだけにする。Resend のエラーは usecase で区別しようがないため。

### 設定（`internal/config/mail.go`）

| 関数 | 環境変数 | 本番の値 |
|---|---|---|
| `NewResendClient()` | `RESEND_API_KEY` | |
| `MailSupportAddress()` | `MAIL_SUPPORT_ADDRESS` | `support@cinelier.app` |
| `MailAdminAddress()` | `MAIL_ADMIN_ADDRESS` | 管理者のアドレス |

- from は役割の名前で持つ。noreply が増えたら `MAIL_NOREPLY_ADDRESS` を足す。
- Resend への送信は、応答を5秒まで待つ。SDK の既定（1分）のままだと、利用者が登録などで長く待たされるため。TMDB と同じ値。

## 送るメール

すべて from `support@cinelier.app`。

| | いつ | to | 送る API |
|---|---|---|---|
| 1 | 登録したとき：確認メール | 登録したアドレス | `POST /users/register`（既存） |
| 2 | メールアドレスを変えたとき：確認メール | 新しいアドレス | `PUT /users/email`（既存） |
| 3 | パスワードを忘れたとき：再設定のリンク | 登録済みのアドレス | パスワード再設定の申請（新規） |
| 4 | 退会したとき：退会の通知 | 退会したユーザーのアドレス | `DELETE /users/`（既存） |
| 5 | お問い合わせを受けたとき（reply_to は問い合わせた人） | 管理者のアドレス | お問い合わせ（新規） |
| 6 | 新しいユーザーの確認が済んだとき：個人情報を含まない通知 | 管理者のアドレス | メールアドレスの確認（新規） |
| 7 | 登録済みのアドレスで登録されたとき：すでに登録されていることの通知 | 登録済みのアドレス | `POST /users/register`（既存） |

## API の形

言語は、映画の API と同じく `?language=ja` で受け取る。

| API | 受け取る値 | 返すもの |
|---|---|---|
| `POST /users/register?language=ja`（変更） | 今と同じ（name、email、password） | 204 |
| `POST /users/verify-email`（新規） | `token` | 成功：204。トークンが違う・切れている：400 |
| `POST /users/verify-email/resend?language=ja`（新規） | `email` | 204 |

- 登録は、登録済みのアドレスでも同じ応答にするため 204 にする。今の 201 と `user_id` は返さなくなるが、ウェブは応答を使っていない。
- 再送は、未確認・未登録・確認済み・60秒以内のどの場合も 204 を返す。どれかだけ違うと、登録の有無がわかるため。アドレスの形が正しくないときは 400、IP ごとの回数制限を超えたときは 429 を返す。これらは登録の有無に関係なく決まる。
- 60秒以内の再送では何も送らないので、ウェブ側で再送のボタンを60秒押せないようにする。
- 確認と再送の API は、既存と同じ形で IP ごとに回数を制限する。回数は登録と同じ1時間に10回。

### 確認用のリンク

- ウェブの画面の URL にトークンを付ける。例：`https://cinelier.app/ja/verify-email?token=...`
- ウェブの画面で「確認する」ボタンが押されたときに、URL のトークンを `POST /users/verify-email` に送る。画面を開いただけでは送らない。メールサービスがリンクを先に自動で開くと、本人が押す前に確認が済んでしまうため。
- トークンは、リフレッシュトークンと同じく `crypto/rand` で作り、DB には SHA-256 のハッシュだけを保存する。
- API はリンクを作るために、ウェブの URL を設定値として持つ。

### 実装で決めたこと

- 確認済みかどうかは `users.email_verified_at`（確認した日時。NULL なら未確認）で持つ。リフレッシュトークンの `revoked_at` と同じ形。
- 確認用のトークンは `email_verification_tokens` に保存する。確認が済んだとき、再送したとき、登録し直したときに、そのユーザーの古いトークンをすべて消す。
- `?language=` がないときは `en` にする。映画の API と同じ。
- 未確認でログインしたときは、パスワードが合っている場合だけ 403（`EMAIL_NOT_VERIFIED`）を返す。パスワードが違えば今までどおり 401。
- 管理者への通知（6）の送信に失敗しても、確認は成功として扱う。退会時の画像の削除と同じく、ログに警告を残す。
- 未確認のユーザーの削除は、既存の定期処理（`CLEANUP_ENABLE`、`CLEANUP_INTERVAL_SECOND`）で行う。
- 再送 API では、未確認のときだけメールを送るので、応答の時間の差は残る。わかるのは「未確認のアカウントがある」ことだけで、そのアカウントは7日で消える。

## メールの見た目

- 全体をベージュ（`--card`）一色にし、文字は紺、ボタンは `--primary`（brown）と `--primary-foreground` にする。色はウェブ（movie-log の `src/styles/globals.css`）に揃える。
- 外側と本文の欄で色を分ける作りにはしない。iPhone の Gmail はダークモードで色を自動で反転させ、メールの側からは止められない。二色にすると反転で明暗が逆になるが、一色なら全体がそのまま暗くなるだけで済む。
- 一番上に、ログイン画面と同じロゴを置く。ロゴはウェブが公開する PNG（`{WEB_BASE_URL}/mail/logo.png`、movie-log#77）を読み込む。
- 画像は反転されないので、Gmail のダークモードではロゴが暗い背景に埋もれて見えにくくなる。本文とボタンは読めるので、これは受け入れる。
- 差出人のアイコンにロゴを出す仕組み（BIMI）は、有料の証明書が必要なので見送る。- メールアプリは `color-mix` や CSS 変数を使えないので、色はあらかじめ16進数に直して書く。
- 今のウェブのお問い合わせのメールの色は使わない。

## DB の変え方

- 正本の `scripts/create_tables.sql` を直し、新しく作る DB には最初から列と表が入るようにする。
- 本番の DB には、変更用の SQL を `psql` で手で1回実行する。その SQL は `docs/infra/logs/` の作業記録に書き、リポジトリに別のファイルとしては置かない。
- あわせて `docs/infra/deployment.md` を最新にする。

## 追加する API

- メールアドレスの確認（メールのリンクのトークンを受け取る）
- 確認メールの再送
- パスワード再設定の申請
- 新しいパスワードの設定
- お問い合わせ
